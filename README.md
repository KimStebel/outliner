# Outliner

A nested to-do list for the browser — Workflowy-shaped, but smaller and faster.
Mobile-first; wider-screen affordances come later.

## Stack

- **Svelte 5** (runes) + **TypeScript** (strict, `noUncheckedIndexedAccess`)
- **Vite 8** dev server and build
- **Vitest** for the model/ops layer
- **Prettier** (`prettier-plugin-svelte`) for formatting

No UI framework and no rich-text editor dependency. Each list row is its own
`contenteditable`, which keeps caret and focus control in our hands — that
control is most of this app.

## Setup

Node 22 is installed via nvm and symlinked into `~/.local/bin` so it resolves in
non-interactive shells (`~/.bashrc` is not sourced there):

```sh
nvm install 22
ln -sf ~/.nvm/versions/node/v22.*/bin/{node,npm,npx} ~/.local/bin/
npm install
```

## Installing it (PWA)

The production build ships a web app manifest and a service worker, so the app
installs to a home screen and works with no network. Everything it needs is
precached, and the document already lives in `localStorage`, so there is
nothing to sync.

The service worker is only registered in a production build — one in front of
the dev server would serve stale modules and fight HMR. To try it:

```sh
npm run build && npm run preview   # also port 8080
```

**It needs a secure context.** Browsers refuse to register a service worker on
plain `http://` to a LAN address, so over `http://<vm-ip>:8080` the app runs
normally but cannot be installed and will not work offline. Any of these fix
it:

- Serve the build over https (a tunnel, or any static host).
- Open it on the host machine at `http://localhost:8080`, which counts as
  secure.
- For testing on a phone, add the origin to
  `chrome://flags/#unsafely-treat-insecure-origin-as-secure`.

`sw.js` is generated at build time by `build/sw-plugin.ts` rather than written
by hand, because the precache list has to name the real content-hashed
filenames. The cache name is derived from that list, so any asset change
produces a new cache and the old one is deleted on activation. Icons are
generated by `npm run icons` and committed, so a normal build needs no browser.

## Sync API

A Rust service (`backend/`) holds one document and hands it back. The document
is ~100KB, so uploading all of it costs less than any scheme for uploading
part of it.

| Request         | Behaviour                                                     |
| --------------- | ------------------------------------------------------------- |
| `GET /api/doc`  | The document, with `ETag` and `Last-Modified`. `404` if none. |
| `HEAD /api/doc` | The same headers, no body. For polling.                       |
| `PUT /api/doc`  | Replace the document. `204` with the new `ETag`.              |

Entity tags are compared on the part that identifies the document, ignoring a
content-coding suffix. Caddy compresses responses and correctly rewrites the
ETag when it does — `"<hash>-gzip"` — and the browser sends that back. Compared
literally it never matches, so every write is refused as stale _and_ every poll
re-downloads the whole document instead of getting a 304. That cost a day of
desktop edits before it was found.

`If-None-Match` on GET/HEAD gives `304`. The ETag is a SHA-256 of the stored
bytes, not an mtime, so a change in the same second as the last poll is still
visible.

**Writes are conditional, and this is the point of the design.** A client that
has been offline holds a whole stale document; uploading it would not merge
badly, it would erase everything done elsewhere. So:

- `PUT` with `If-Match: <etag>` succeeds only if that is still current, else
  `412` — with the live `ETag` attached so the caller can refetch.
- `PUT` with no `If-Match` is accepted only when nothing is stored yet; against
  an existing document it is `428`.

**Auth is Caddy's job**, not the service's. Caddy enforces HTTP basic auth on
`/api/*` and the service is never published outside the compose network — it
has no authentication of its own, so exposing its port would expose the
document. Credentials live in `prod-basic-auth` (gitignored) and are hashed
locally at deploy time, so the plaintext never reaches the server.

Reads are not logged — polling every ten seconds would bury everything else —
but every write is, successful or refused. A refusal is the interesting one:
it is the moment two devices diverged, and the losing one is about to have its
copy replaced. The line records what the client offered against what the
server held, so "did I lose an edit?" has an answer.

Writes are atomic: temp file, `fsync`, rename, `fsync` the directory, keeping
the displaced copy as `doc.json.bak`. A crash mid-write cannot leave a
truncated document, which would otherwise be pulled over a client's good local
copy.

### The client

`sync.ts` is the state machine, free of Svelte and the DOM so it can be tested
against a fake transport; `httpSync.ts` is the HTTP half; `SyncIndicator.svelte`
shows the result.

- **An upload that would change nothing is skipped.** The whole document goes
  up every time, so this matters: a no-op operation (Shift-Tab at the top
  level) or typing a character and deleting it still mark the document dirty
  while leaving it byte-identical. The client compares against the bytes the
  server is known to hold, so those cost nothing at all.
- Edits upload after **5 seconds of quiet**, and the timer restarts on every
  keystroke. The page being hidden flushes immediately.
- The server is polled every **10 seconds** while the tab is in the foreground,
  and once more the moment it returns. Hidden tabs do not poll.
- The "Updated" notice is **transient**: it clears when the user edits again
  or when a save succeeds. Left sticky it reported "Updated" over a document
  that had just been saved, which reads as though the edit went nowhere.
- **The server wins a conflict.** A refused upload means the local copy is
  replaced. The displaced version is kept at `outliner:replaced-backup` in
  localStorage — one copy, as a way back from a surprise, not a history.
- A server copy that fails validation is **ignored rather than adopted**, so a
  corrupt file cannot destroy a good local document.
- Clicks on a link are handled explicitly, including middle click: `click` fires
  only for the primary button, and inside a `contenteditable` the browser's own
  middle-button default is not "open in a new tab" but, on Linux, pasting the
  primary selection into the row. The pointerdown that keeps a tap on a link
  from focusing the row is suppressed for the primary button only, so the right
  button keeps its menu.

`401` is its own state, not a retry loop: it offers a **Sign in** action that
opens the API as a _navigation_, which is what makes the browser show its
basic-auth prompt. A `fetch` that gets a 401 does not reliably raise it.

The flush on hide is a plain `fetch`, deliberately not `keepalive`: keepalive
bodies are capped at 64KB, which this document can exceed, so it would fail
exactly when it matters. If the page dies before the request completes nothing
is lost — the edit is in localStorage and uploads on next launch.

A local edit made _while_ a reconcile request is in flight is discarded when
that request turns out to carry a newer document — server-wins applies to it
like any other. The displaced copy goes to `outliner:replaced-backup`. The
window is a few hundred milliseconds, and polls do not run while there are
unsaved edits, so this needs an edit landing inside the request itself.

**First sync is the one dangerous moment.** Server-wins means the first device
to upload defines the document, and any other device then adopts it, discarding
whatever it had. Open the device holding the authoritative list first.

## Auth

[Rauthy](https://github.com/sebadob/rauthy) — an OIDC provider — runs
alongside the app, and the backend validates JWTs against its JWKS. The point
of doing it that way is that Rauthy is not in the path of an API call: the
backend caches the public keys and verifies signatures itself, so Rauthy being
down does not stop a client that already holds a token.

A valid bearer token is now the only way to reach the document. Caddy
authenticates nothing, and the backend **refuses to start** without an issuer
configured rather than serving the document unprotected — `AUTH_DISABLED=true`
is the one way round that, which only the test harness uses.

Rauthy is mounted at **`/auth` on the app's own origin**, not on a subdomain.
All of its routes already live under `/auth`, and its issuer is always
`<pub_url>/auth/v1/`, so nothing needs rewriting. That means no second
certificate or DNS record, the app's `connect-src 'self'` CSP stays as it is,
and the local setup has the same shape as production — Caddy routes `/auth/*`
there in production, the Vite proxy does locally.

### Running it locally

Two ways, for two kinds of question.

```sh
npm run stack         # Caddy + backend + Rauthy, exactly as production runs
npm run verify:stack
```

`npm run stack` is the one to reach for when the question involves the proxy:
the auth rules, the headers, the service worker, compression and ETags. It
uses the same Caddyfile, the same images and the same routes as production —
only the address differs (`:8080` over plain HTTP rather than a hostname with
a certificate).

```sh
npm run auth          # Rauthy alone, proxied to /auth by the dev server
npm run dev
npm run verify:oidc
```

That second pair is the faster loop for working on the app itself, with HMR.

Bootstrap data is applied with a plain `INSERT` against an empty database, so
editing `deploy/rauthy/bootstrap/*.json` does nothing to a database that
already exists. Pass `--reset` after changing it.

editing `deploy/rauthy/bootstrap/*.json` does nothing to a database that

`deploy/rauthy/config.toml` is shared by local and production; everything that

`RP_ORIGIN`, and every secret — arrives as an environment override instead.

### How a request is authenticated

Mid-move, so there are two ways in:

- A **bearer token** is validated by the backend (`backend/src/auth.rs`)
  against Rauthy's published keys. Caddy deliberately does _not_ ask such a
  request for basic credentials — it would refuse it before the backend ever
  saw the token — which is what the `@unauthenticated` matcher in the
  Caddyfile is for.
- **Anything else** has to pass Caddy's basic auth, which is what keeps a
  client that has not signed in yet working. That half goes away with the
  cut-over.

Only Ed25519 is accepted and the algorithm is never taken from the token. The
classic JWT failures — `alg: none`, an RSA public key replayed as an HMAC
secret — all come from letting the token choose how it gets verified.

And signature checking is not authorisation: a valid token only proves Rauthy
issued it to _somebody_. `AUTH_SUBJECTS` says which somebody. Without that,
turning on self sign-up would hand write access to anyone who registered.

### Two things that are easy to get wrong

**Access tokens cannot last longer than 24 hours.** Rauthy validates
`10 <= access_token_lifetime <= 86400`, and there is no global override. A
month-long session is reached with a 30 day _refresh_ token instead, which the
app redeems silently; a password is then only needed once a month.

**A refresh token is not valid when it is issued.** Rauthy sets
`nbf = now + access_token_lifetime - 60s` and `exp = nbf + refresh_token_lifetime`,
so it can only be redeemed in the last minute of the access token's life or
after it has expired. Refreshing at half-life — the usual advice — returns 401
every time. It also means `exp - iat` is a month _plus_ a day, not a month.

The signing keys rotate on the 1st of each month and this **cannot be
disabled**, so anything caching the JWKS has to refetch when it meets an
unknown `kid`, or it breaks monthly. Superseded keys are kept for 90 days, so
tokens issued before a rotation stay verifiable.

## Deployment

Live at **https://outliner.stebel.kim**, served by Caddy in Docker.

```sh
npm run deploy   # build, rsync, restart Caddy
npm run smoke    # verify the deployed site
```

The build happens locally and `dist/` is rsynced to the server, so the server
needs no Node toolchain and a deploy is just a file copy. Caddy obtains and
renews the certificate itself; `deploy/Caddyfile` and
`deploy/docker-compose.yml` are the whole server config.

Two things worth knowing about this particular box:

- **Everything lives under `/home/outliner`, not `/opt`.** Docker here is the
  Canonical snap, and snap confinement grants it the `home` interface only —
  from `/opt` the CLI cannot read the compose file and the daemon cannot
  bind-mount the site directory. It fails with a confusing "no configuration
  file provided".
- **The `caddy-data` volume holds the certificates.** Deleting it forces
  re-issuance on the next start, which will hit Let's Encrypt rate limits if
  it happens repeatedly.

Caching is split so deploys actually reach people: hashed files under
`/assets/` are immutable for a year, while `/`, `/sw.js` and the manifest are
`no-cache`. If the shell or the worker were cached, a deploy would keep
serving the previous build indefinitely.

Credentials come from `prod-env` in the project root, which is gitignored:

```
ip: <address>
user: <user>
password: <password>
```

`prod-basic-auth` is no longer used by anything; basic auth is gone.

Two more gitignored files: `prod-rauthy-env` holds the identity provider's
secrets, and `prod-rauthy-user` the account's password. Both are generated by
`./scripts/deploy.sh --first-run` and then left alone. A normal deploy needs
only `prod-rauthy-env`; the account password is used by the deployment check
and the backup inspection, not by deploying.

**A normal deploy refuses to run if either is missing**, rather than
generating a replacement. Bootstrap data only ever applies to an _empty_
Rauthy database, so a regenerated file cannot take effect against a live
deployment: a new password simply would not work while claiming to be the
password, and new `ENC_KEYS` could not read the existing database at all.
Both failures are silent at deploy time, which is why the script would rather
stop. Keep both in a password manager **and** on disk.

### Rauthy's configuration has sharp edges

Three of these cost a deploy each before `npm run deploy` learned to validate
the provider's configuration locally first — it now runs `validate-config`
through the production compose file before uploading anything, which catches
the first two.

- **`ENC_KEYS` must be real base64 of exactly 32 bytes.** The first attempt
  generated it by stripping `/`, `+` and `=` out of a base64 string, which
  does not leave a shorter base64 string — it leaves something that does not
  decode. Rauthy refuses to start with `Invalid ENC_KEYS`.
- **`rp_origin` needs an explicit port.** Rauthy splits it on the last colon
  and parses the remainder as a port, so `https://outliner.stebel.kim` is read
  as having the port `//outliner.stebel.kim`. It wants
  `https://outliner.stebel.kim:443`.
- **Bootstrap files must be readable by uid 10001**, which is what Rauthy runs
  as. rsync's `--chmod=F600` left them owned by the deploying user, and Rauthy
  says _nothing at all_ when it cannot read them: the database initialised
  cleanly, with no client and no user, and every login 404'd. The deployment
  check now asks whether the client is registered, because that failure is
  otherwise completely silent.

**A deploy does not touch accounts.** It ships the client definition and
nothing else, so it cannot create, replace or disturb a user — Rauthy holds
them, and they are managed in its admin UI at `/auth/v1/admin`. The one
account is seeded only by `--first-run`, when there is no database and no
admin UI to reach yet.

Bootstrap data is applied once, with a plain `INSERT` against an empty
database. Changing a client afterwards means the admin UI, or removing the
`rauthy-data` volume to start over — which also discards the signing keys, so
every issued token stops verifying.

The seeded account's id is pinned and must match `AUTH_SUBJECTS` in the
compose file, since that is what the backend authorises against. A user
created later through the admin UI gets a random id, so `AUTH_SUBJECTS` would
need updating to match it.

The `rauthy-data` volume is the one worth backing up: it holds the account and
the signing keys.

## Backups

Daily, to Cloudflare R2 (`outliner-backups`), keeping ten.

```sh
npm run backups   # what is in the bucket, and is the newest one any good
```

### Keep the secrets somewhere else

`prod-rauthy-env`, `prod-rauthy-user` and `prod-env` exist **only on the
developer's machine**, and `prod-rauthy-env` holds `ENC_KEYS` — which is what
Rauthy's database _and its backups_ are encrypted with. Without that file the
backups are a bucket of ciphertext.

They belong in a password manager, and deliberately **not** in the backup
bucket: putting the key next to the ciphertext defeats the point of Rauthy
encrypting it. As it stands, losing the laptop costs more than losing the
server.

### Two mechanisms, because one already existed

**Rauthy backs up its own database** at 02:30 (`HQL_BACKUP_CRON`), straight to
R2, keeping ten days (`HQL_BACKUP_KEEP_FOR`). Those are real SQLite snapshots
rather than copies of a live file — which can be torn — encrypted, and
integrity-checked on restore. Better than anything written here, so it is left
to do it. It also keeps three days locally on the server, which is a free
second line of defence.

**`deploy/backup-doc.sh` handles the document**, which nothing else covers. It
runs at 03:15 from `outliner-backup.timer`, as `doc/YYYY-MM-DD.json.gz`.

Nothing was installed for either: `curl` on the server signs its own S3
requests with `--aws-sigv4`, and `python3` only picks keys out of a listing.
`deploy.sh` writes `r2.env`, which Rauthy reads as an `env_file` and the script
sources, so the credentials live in one place.

The document needs no snapshotting — the backend writes it atomically, so the
file on disk is always a complete version. A corrupt or unparseable document
**fails** the backup rather than being uploaded, so ten days of good history
cannot be overwritten by wreckage.

Sharing one bucket is safe: Hiqlite lists the whole bucket when it prunes, but
only deletes keys matching its own `backup_node_<id>_<ts>.sqlite` pattern, so
`doc/` is left alone.

### Retention is by count, not by age

Ten _objects_, not "anything older than ten days". With a daily run they are
the same, but they fail differently: if the timer stops, age-based expiry
eventually leaves nothing, while keeping the newest ten leaves those ten until
someone notices. Rauthy only offers age-based, so its own backups do expire.

### Restoring

Written down, deliberately never run against production.

**The document.** Download the object, gunzip it, write it to
`/home/outliner/data/doc.json`, `chown 10001:10001`, restart the backend.

But first: **a restore propagates to every device.** They poll with their
stored ETag, see a different one, and adopt the server's copy — server-wins is
the design. So restoring a ten-day-old document overwrites newer local copies
everywhere. The displaced version does land in `outliner:replaced-backup` in
localStorage, which is the escape hatch.

So the first question in a real restore is always _does some device still have
the good version?_ If so, sync from that device instead.

**Rauthy.** Stop the stack, set `HQL_BACKUP_RESTORE=s3:<object>`, start it,
then remove the variable and restart. Needs the same `ENC_KEYS`.

### What this does not tell you

**If the timer stops, nothing says so.** `npm run backups` reports the age of
the newest backup, but only when someone runs it. Keeping the newest ten at
least means a stall does not eat the existing backups.

Rauthy's backups also cannot be verified without restoring them — they are
encrypted blobs, so `npm run backups` only confirms they exist, are a
plausible size, and are recent. The account is recreatable from
`prod-rauthy-user`, so that is a gap rather than a covered case.

## Testing

Three layers, each against something it owns:

| Layer                     | Against                                  | Writes to           |
| ------------------------- | ---------------------------------------- | ------------------- |
| `cargo test` / `npm test` | nothing — pure logic and a temp dir      | nothing             |
| `npm run e2e`             | a preview server and a backend it starts | its own scratch dir |
| `npm run verify:oidc`     | a local Rauthy it expects to be running  | its own database    |
| `npm run verify:stack`    | the whole local stack, through Caddy     | its own database    |
| `npm run smoke`           | the real deployment                      | **nothing**         |

`npm run e2e` starts a real sync backend on a temporary directory, so the 147
checks run against working sync rather than a dead endpoint — including an
edit reaching the server, a second client picking it up, and a stale write
being refused and resolved in the server's favour.

`npm run smoke` answers one question: _did the deployment land?_ The right
build, a valid certificate, the headers, auth enforced on the API and absent
on the site, the service worker, offline. Behaviour is not its job.

It signs in for real now, because a token is the only way to read the
document — so every deploy also proves the login flow works against the live
site, which nothing automated did before. It needs `prod-rauthy-user` for
that, and stays read-only: the app is intercepted so it cannot load, since
loading it would start sync, and sync writes.

**It writes nothing, and proves it.** Writes are blocked at the network layer,
and the stored document's ETag is compared before and after. This matters
because an earlier version of this suite ran the full behaviour test against
production and destroyed the document it was meant to be checking — the
behaviour it tested was already covered by `cargo test`, so the risk bought
nothing.

`npm run verify:oidc` exists because the backend's token validation is about
to depend on a dozen details of Rauthy's behaviour — the exact issuer string,
which claim marks an access token, whether Ed25519 verification against the
published JWKS actually works. It asserts all of them against a real Rauthy
before any of it is written in Rust, where the same mistake is far harder to
see. Two of those details were wrong when first read from the docs.

`npm run verify:stack` covers what only exists once everything is wired
together, and it has earned its place twice over. It caught the backend's data
volume arriving owned by root — production only worked because the deploy
script chowned a host directory — and it caught `fetch` being stored unbound,
which throws `Illegal invocation` in a browser and is perfectly happy in Node,
so all 322 unit tests passed while signing in could not work at all.

The build-identity check is the one that earns the suite its keep: "the deploy
silently did not take effect" has happened twice here, once from a file
watcher that saw nothing and once from a Caddy that was never reloaded.

## Architecture

**Flat document model.** Items live in a `Record<ItemId, Item>` with ordered
`children` arrays, not as nested objects — indent, outdent, move, and
delete-subtree then touch only a couple of records instead of rebuilding a tree.
Rendering flattens the visible tree into an array of `(id, depth)` rows, which
is also the shape windowing would need if lists get large enough to warrant it.

**Ops layer.** Every mutation goes through an operation that can produce its own
inverse, feeding an app-level undo stack. This is load-bearing rather than
optional polish: per-item `contenteditable` means the browser's native undo does
not span structural edits, and a mis-triggered swipe deletes a whole subtree.

**Journalled inverses, not hand-written ones.** Rather than writing an undo for
each op, every op runs inside a `Tx` (`tx.ts`) that snapshots the _before_ image
of each record it touches. The inverse of any op — however many records it
rewrites — is then just "put these records back". Flat records keep each journal
entry small enough to produce on every keystroke.

**Total ops.** An operation that cannot apply (outdent at the top level, indent
of a first child) is a no-op returning `null` rather than an error, so the UI can
bind keys without pre-checking. No-ops record no history and, importantly, leave
the redo stack intact.

### Layout

| File            | Role                                                        |
| --------------- | ----------------------------------------------------------- |
| `model.ts`      | Types, plus pure tree/visible-order queries. No mutation.   |
| `tx.ts`         | Change journalling, revert/reapply, coalescing of changes.  |
| `ops.ts`        | Editing semantics. Takes a `Tx`, returns a caret or `null`. |
| `store.ts`      | `DocStore`: owns doc, caret, and undo/redo stacks.          |
| `persist.ts`    | Versioned envelope and a validating loader.                 |
| `storage.ts`    | Debounced, typed `Storage` wrapper.                         |
| `test-utils.ts` | Outline notation (`a` / `  b` / `> collapsed`) for tests.   |

Nothing below `store.ts` imports Svelte, so the whole core is testable in plain
Node. `editor.svelte.ts` is the only seam: it wraps the `Doc` in `$state`, and
because ops mutate records in place, Svelte's deep proxy invalidates only the
fields actually touched. Typing changes `item.text`, which no layout code reads,
so a keystroke does not recompute the row list.

### The header

Undo, redo and fold-all sit on the header because they are used constantly.
Everything rarer goes behind the `...` menu (`src/lib/Menu.svelte`), which
takes its entries as data rather than markup — adding one is a line in the
array in `App.svelte`, and the fiddly parts stay in the component: closing on
an outside tap, Escape returning focus to the trigger, and arrow keys between
items.

### The UI layer

| File                 | Role                                                  |
| -------------------- | ----------------------------------------------------- |
| `editor.svelte.ts`   | Wraps the doc in `$state` and hands it to the store.  |
| `caret.ts`           | DOM selection <-> character offsets; line geometry.   |
| `Outline.svelte`     | Renders rows; owns all key, input and paste handling. |
| `Row.svelte`         | One row: bullet plus its `contenteditable`.           |
| `KeyboardBar.svelte` | Indent/outdent docked above the on-screen keyboard.   |
| `welcome.ts`         | The first-run document.                               |

Three things carry the weight here:

**The editable's text is never interpolated in the markup.** `Row.svelte` writes
it with an effect, and only when it diverges from the model. If Svelte owned the
text node it would replace it on every keystroke and destroy the caret; writing
only on divergence makes typing a no-op while still letting undo, merge and
paste land.

**Events are delegated to the container**, so adding a row costs no listeners
and handlers can find their row from `data-item-id`.

**Arrow keys consult geometry, not offsets.** Inside a row whose text wraps, the
browser should keep moving the caret and we only take over at the real first or
last visual line — an `offset === 0` test would jump rows from the middle of a
wrapped line.

**The keyboard bar is positioned against the visual viewport.** `position:
fixed` resolves against the _layout_ viewport, which does not shrink when the
keyboard opens, so a bar pinned to `bottom: 0` ends up behind the keyboard. The
bar instead sits at the bottom of a click-through wrapper whose height tracks
`visualViewport.offsetTop + height`. Its buttons act on `pointerdown` with the
default suppressed: allowing the default would move focus to the button, blur
the row, close the keyboard, and unmount the bar before a `click` could ever
arrive.

### Editing semantics worth knowing

- **Enter** splits at the caret. At offset 0 of a non-empty item it pushes the
  line down (empty sibling above, caret stays). On an item with _visible_
  children the tail becomes the new first child, since the children belong to
  the head.
- **Shift-Tab** adopts any following siblings as children. Without that, outdent
  would silently reorder the document on screen.
- **Backspace at offset 0** merges into the previous _visible_ row, children and
  all. Merging a first child into its parent leaves the children in the slot the
  item vacated, so the following siblings keep their place; otherwise they are
  appended to the destination, which is the deepest row before this one and so
  preserves document order. The destination is expanded if it adopts children,
  since dropping them into a collapsed item would look like deletion.
- **Typing coalesces** into one undo step per item within a 600 ms window, so
  undo is not per-character. A structural edit or a caret move breaks the step.
- The document is never left empty; deleting the last item creates a fresh one.
- **Pasting multi-line text makes multiple rows**, in one undo step. A row holds
  one line by definition, so flattening the breaks would silently discard the
  structure that was just pasted. Paste is always intercepted and reduced to
  `text/plain`.
- **Tapping below the list** appends a sibling of the last row — the same thing
  pressing Enter there would do.
- **Long-press anywhere on a row to drag it** on touch, so the small bullet is
  not the only handle. The hold is 400ms — under the ~500ms at which phones
  start selecting text, so the drag wins that race — and any movement before it
  elapses cancels it, leaving scrolling and swipe-to-delete untouched. This
  applies to a row being edited too: dismissing the keyboard does not blur the
  row, so exempting focused rows left the last row touched undraggable until
  something else was tapped. The cost is hold-to-select inside a focused row;
  a double tap still selects a word.
- **Drag a bullet to move an item**, children included. Vertical travel picks
  the gap between rows; horizontal travel picks the depth, which is what makes
  a drag able to re-parent rather than only reorder. The depth is clamped to
  what the neighbours allow: at most one level deeper than the row above (there
  is no intermediate item to adopt you), and never shallower than the row below
  (which would leave that row under a parent it does not belong to). Moving an
  item into its own subtree is refused.
- **Bare URLs, `www.` hosts and email addresses become links.** The rendered
  characters stay identical to the stored ones — links are decoration, not
  substitution — because every caret offset is an index into `item.text`. Only
  `http`, `https` and `mailto` are allowed through; the scheme is checked by
  URL parsing, so a `javascript:` href can never reach the document. A URL
  typed just now becomes a link when the row loses focus.
- **Markdown import** (header button) understands heading level and list
  indentation as nesting, and also plain indented text. Items are appended, so
  an import can never destroy what is there, and the whole thing is one undo
  step. Inline syntax is kept verbatim: rows store what you see, so `**bold**`
  and `[label](url)` stay as written — the URL inside the latter is still
  clickable. Task markers `[ ]` / `[x]` are kept as text, since there is no
  done state to map them onto yet.
- **On touch the fold chevron sits at the far end of the row**, opposite the
  zoom dot. Side by side a thumb catches the wrong one, and they do very
  different things — one folds in place, the other replaces the whole view.
  With a fine pointer it stays in the gutter, where taps are precise and the
  row keeps the width.
- **Tap a row's dot to zoom into it**: the view re-roots on that item, its
  children render at depth 0, and a breadcrumb trails back out. Escape zooms
  out one level. The fold chevron and the zoom dot are deliberately separate
  controls — one tap cannot mean two things, and both double as drag handles.
  While zoomed, navigation, Backspace-merge and outdent all stop at the zoom
  boundary rather than quietly acting on rows that are off screen.
  The zoom is not persisted: a stored zoom could point at an item deleted
  elsewhere, and opening into an unexpected subtree is worse than starting at
  the top. The zoomed item's title is read-only; zoom out one level to edit it.
- **Collapse all** in the header folds every parent at once, and turns into
  expand-all once everything is folded — a collapse-only button would leave no
  way back but opening each row by hand. It is one undo step, and records
  nothing when there is nothing to change.
- **Tap a bullet to fold or unfold** its children. A parent's bullet is a
  chevron — pointing down when open, right when folded — so the state is
  readable at a glance; a leaf keeps a plain dot, since a chevron there would
  advertise an action that does not exist. The bullet occupies a fixed-width
  slot either way, so a parent's text and a leaf's text at the same depth
  still start at the same x.
- **Indent and outdent on mobile** come from a bar docked above the keyboard; a
  phone keyboard has no Tab key, so there is no other way to nest. It shows
  whenever a row is focused on a touch device, and its buttons disable
  themselves when the operation would be a no-op.
- **Duplicate** copies a row and everything under it, placing the copy
  directly after the original, with the caret on the copy — duplicating is
  nearly always the first half of editing the copy. Fold state is copied too,
  so duplicating a folded branch does not suddenly unfold a screenful.
  Ctrl/Cmd-D does the same from a keyboard, since the bar is touch-only.
- **Swipe a row right to delete it and its children.** The gesture locks
  direction after 8px and only claims clearly rightward travel, so vertical
  scrolling is untouched; it commits past 35% of the row's width. Mouse drags
  are ignored, since inside a row those are text selection.
  **Ctrl/Cmd-Enter** does the same from a keyboard, so deleting a subtree is
  not touch-only. Undo is the header button or Ctrl/Cmd-Z.
- **After a delete the caret moves to the row _below_** the deleted subtree, at
  its start, so the list closes up under the caret and editing carries on
  downwards. It falls back to the end of the preceding row only when nothing
  follows. Note this cannot use `nextVisible`: for a parent that returns its
  own first child, which is inside the subtree being deleted.
- **Deleting by swipe does not move focus.** Focusing a neighbouring row would
  pop the keyboard open over a list the user was only tidying. The keyboard
  shortcut does keep the caret, because there the user is demonstrably typing.

`contenteditable="plaintext-only"` is used where supported, but it is
feature-detected rather than assumed: an unrecognised value maps to `inherit`,
which would leave rows _not editable at all_. The fallback is `true` plus our
own paste interception and suppression of the bold/italic/underline shortcuts.
